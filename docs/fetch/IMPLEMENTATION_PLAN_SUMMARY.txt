🎯 KEY DESIGN DECISIONS
═══════════════════════════════════════════════════════════════════════════════════════

1. ✓ Use typing.Protocol (duck typing) instead of ABC
   Rationale: Flexible across libraries, no base class coupling, matches unearth

2. ✓ Keep requests as default (RequestsFetcher wrapper)
   Rationale: Zero breaking changes, gradual adoption, full backward compatibility

3. ✓ Three-tier implementation:
   • Phase 1a: RequestsFetcher (builtin, core)
   • Phase 1b: HttpxFetcher (HTTP/2, separate package: conda-httpx)
   • Phase 1c: CurlFetcher (multiplexing, separate package: conda-curl)

4. ✓ Unified exception hierarchy
   Rationale: Single mapping point for all library exceptions to conda exceptions

5. ✓ Thin Session wrapper (optional)
   Rationale: 100% backward compatibility, can delegate to fetcher internally

❓ FAQ
═══════════════════════════════════════════════════════════════════════════════════════

Q: What's the difference between RequestsFetcher and CondaSession?
A: RequestsFetcher is a new abstraction that wraps requests.Session to implement
   the Fetcher protocol. CondaSession can stay unchanged for backward compatibility,
   or optionally become a thin wrapper around a fetcher.

Q: Will this break existing code?
A: No. Phase 1a is fully backward compatible. Requests stays the default, and
   existing Session/download APIs continue to work unchanged.

Q: When do we get HTTP/2 support?
A: HTTP/2 support comes in Phase 1b (HttpxFetcher in separate conda-httpx package),
   estimated 1-2 weeks after Phase 1a is complete.

Q: Can I use this with httpx today?
A: Not yet. Phase 1a is the foundation (RequestsFetcher). Phase 1b adds HttpxFetcher.
   You can follow the templates in PLUGGABLE_REQUESTS_QUICK_START.md to create one now.

Q: What about multiplexing/concurrent downloads?
A: Multiplexing comes in Phase 1c (CurlFetcher), which implements the optional
   FetcherMultiplexer protocol. See PLUGGABLE_REQUESTS_ARCHITECTURE.md for details.

Q: How do I know if this is compatible with my auth setup?
A: ChannelAuthResolver maps existing conda auth plugins transparently. Existing
   ChannelAuthBase plugins continue to work without changes.

Q: Is this production-ready?
A: Phase 1a creates the foundation and is ready for production (through extensive
   testing). HTTP/2 support (1b) and multiplexing (1c) come in future phases.
